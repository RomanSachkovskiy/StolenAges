# STOLEN AGES — исследование перехода к real-time with pause (RTwP)

**Статус:** исследование архитектуры для будущих версий. **НЕ реализовывать полноценный RTwP в v0.1.0.** В v0.1 обязательна законченная пошаговая игра по `GAME_SPEC_V0.1.md`, но игровое ядро проектируется независимым от рендера, FPS и браузерных таймеров.

## 1. Краткий вывод

**RTwP для Stolen Ages технически реализуем** на TypeScript + Phaser + GitHub Pages без сервера, пока игра одиночная. Игрок сможет останавливать игровое время, выделять армии и города, отдавать несколько приказов, видеть их маршруты и стоимость, затем запускать симуляцию. Приказы в паузе записываются и валидируются, но не начинают движение, производство, бой или захват до возобновления времени. В будущем пригодятся скорости x1/x2/x4 и автопауза на важных событиях.

**Рекомендация:** выпустить v0.1 как пошаговую стратегию; сразу разделить `commands -> validation -> deterministic simulation -> events -> UI`. Затем выпустить небольшой эксперимент RTwP на отдельной ветке. Не обещать бесшовную замену правил: движок и модели можно переиспользовать, однако баланс, временные стоимости, управление ИИ и UX потребуют отдельной настройки.

## 2. Сравнение режимов

| Критерий | Пошаговая v0.1 | Полный realtime | RTwP |
|---|---|---|---|
| Контроль игрока | Высокий | Ниже, особенно на телефоне | Высокий благодаря паузе |
| Управление в портретном формате | Простое | Перегружено | Возможно с очередью приказов |
| Стоимость MVP | Наименьшая | Выше | Средне-высокая |
| Тестируемость/баланс | Легче | Сложнее | Сложнее, но возможно с fixed tick |
| Ощущение живого мира | Среднее | Высокое | Высокое |
| Пауза при сворачивании вкладки | Естественная | Нужно обеспечить | Обязательна |
| Риск снежного кома | Ограничен AP | Повышен | Повышен без ограничений производства |

Главное: **без ходов и AP ≠ без ограничений**. Игру удерживают стоимость ресурсов, лимиты мощностей, время строительства, расстояния, снабжение, зоны контроля и перезарядки приказов. Если просто убрать AP, победит раннее спам-производство.

## 3. Рекомендуемая симуляция

- Логическое игровое время `gameTimeMs` не связано с `Date.now`, FPS или CSS-анимациями.
- Постоянный логический шаг `SIM_DT_MS = 100` либо `200` (проверить профилированием). На x1 движок выполняет 10 или 5 шагов/игровую секунду; на x2/x4 — соответственно больше шагов при том же реальном времени. Оптимизированные симуляционные подсистемы могут обновляться раз в 500–1000 мс по накопителю.
- `requestAnimationFrame` управляет лишь рендером и накопителем игрового времени. При большом лаге/возврате вкладки нельзя догонять часы неограниченным числом тиков: ограничить `maxTicksPerFrame`, остаток распределять или останавливать с уведомлением.
- `pause` означает **0 advancement тиков**, но камера/панели/выделение/постановка приказов работают.
- При `visibilitychange -> hidden` сохранять состояние и автоматически останавливать одиночную игру. При возвращении не компенсировать пропущенное wall time.
- Для воспроизводимости все изменения состояния проходят через детерминированный engine с явно сериализуемым PRNG state. Никаких `Math.random()` внутри симуляции.

Псевдокод:

```ts
function frame(realDeltaMs: number) {
  if (clock.paused) return render(state);
  accumulator += Math.min(realDeltaMs, 250) * clock.speed;
  let ticks = 0;
  while (accumulator >= SIM_DT_MS && ticks < MAX_TICKS_PER_FRAME) {
    state = simulateTick(state, SIM_DT_MS, dequeueDueCommands(), rng);
    accumulator -= SIM_DT_MS;
    ticks++;
  }
  renderInterpolated(state, accumulator / SIM_DT_MS);
}
```

**Важное уточнение:** упорядоченность ввода и RNG должна быть зафиксирована. Если queue пополняется в процессе кадра, присваивать `sequenceId`; применение на ближайшем tick с сортировкой `(scheduledTick, playerId, sequenceId)`.

## 4. Командная модель — проектировать уже в v0.1

Пример контрактов:

```ts
type GameCommand =
  | { kind: 'Build'; playerId: string; epoch: 'Past'|'Present'|'Future'; regionId: string; buildingId: string }
  | { kind: 'Recruit'; playerId: string; epoch: string; regionId: string; unitType: string }
  | { kind: 'MoveArmy'; playerId: string; armyId: string; targetRegionId: string }
  | { kind: 'Upgrade'; playerId: string; entityId: string }
  | { kind: 'StartResearch'; playerId: string; techId: string };

type ScheduledCommand = {
  id: string;
  command: GameCommand;
  scheduledTick: number;
  sequenceId: number;
  status: 'queued'|'active'|'completed'|'rejected'|'cancelled';
};

type GameEvent = {
  tick: number;
  type: string;
  payload: Record<string, unknown>;
};
```

В **v0.1** тот же `validateCommand`, `applyCommand`, `emitEvents` используются в пошаговом обработчике; `EndRound` повышает абстрактный `simulationStep`, решает доход/стройку/осады. Для RTwP появится `simulateTick`, которое исполняет активные длительные задачи по игровым секундам. **Не внедрять фиктивные таймеры и очередь в видимую игру v0.1 только ради будущего.** Достаточно чистого интерфейса и отделения domain от Phaser.

## 5. Семантика приказов на паузе

1. Игрок нажимает **Pause** (или клавишу Space на ПК), карта замирает; анимация движения и прогресс процессов остановлены.
2. Можно выбрать несколько армий, отметить путь, назначить стройку/исследование. UI сразу показывает будущие маршруты, цену и конфликты приказов.
3. Приказ резервирует ресурсы в момент принятия либо помечается как `pendingFunding` (нужно выбрать **одну** схему; для первой RTwP-версии рекомендуется **резервирование** — меньше неожиданных отказов).
4. Игрок может переставить очередность/отменить приказ; до старта действия резерв возвращается полностью. Если уже пошёл процесс, возврат зависит от правил (например, 50% за недостроенную стройку).
5. Снимаем паузу: начинают выполняться команды, время движется и AI действует одновременно. На паузе AI не получает скрытых тиков.
6. При столкновении армий/конце стройки/потере столицы/осаде можно сделать **автопаузу**, чтобы игрок принял решение.

**На смартфоне** кнопка паузы постоянно доступна в верхнем HUD; нижний sheet показывает очередь и кнопку «Запустить». Во время паузы жесты карты и управление не блокируются. Не смешивать паузу с раскрытием обычного меню.

## 6. Системы, которые изменятся при миграции

### Экономика и строительство

Все доходы и содержание конвертируются из `perRound` в `perGameSecond`: например, если позднее один круг эквивалентен 60 игровым секундам, доход фермы `+2/round` станет `+2/60 units/sec`. Это **начальная калибровка, не готовый баланс**. Использовать целочисленные единицы и накопитель дробного прогресса, чтобы результат не зависел от длины тика. Стройка длится N секунд и может параллелиться лишь при явно ограниченной мощности региона.

### Армии и бой

Марш проходит по рёбрам графа с фиксированной стоимостью в игровых секундах, замедлением на местности и мостах, снабжением и зоны контроля; бой начинает событие встречи. Для первой RTwP-версии подходит абстрактное сражение с длительностью 5–15 игровых секунд и периодическими событиями урона — **без физического моделирования пуль/мечей**. Сильные крепости требуют осады с видимым progress и возможностью снять блокаду.

### ИИ

ИИ обновляет план каждые X игровых секунд и немедленно по критическим событиям, но имеет бюджет вычислений. Использует те же проверки, стоимость и задержки. На скорости x4 относительная игровая частота решений не должна уменьшаться. Возможна пауза расчётов или планирования игрока, но **не преимущество скрытого производства у ИИ**.

### Временные эхо-эффекты

Past -> Present -> Future остаётся **ациклической** причинной зависимостью. При смене здания или владельца переподсчитать бонусы на **следующем** тике экономики, без повторного начисления уже прошедшего. Не переносить автоматически войска и регионы между эпохами.

## 7. Риски и способы снижения

- **Микроменеджмент на телефоне:** ограничить число одновременно активных армий; добавить групповой приказ, очередь, приоритетные события и автопаузу.
- **Снежный ком:** лимиты стройплощадок, растущее содержание, cap вооружённых групп, длинные логистические пути, ранний мирный нейтральный буфер; отставшему дать оборонный шанс, а не бесплатную армию.
- **Быстрая скорость ломает ИИ:** считать по игровому времени, профилировать худшие кадры на слабом Android; ограничивать расчёт маршрутов.
- **Фоновая вкладка:** скрытие всегда ставит офлайновую игру на паузу и делает autosave, не начисляет ресурсы от реального времени вне вкладки.
- **Сохранение во время действий:** сериализовать очереди, RNG, `gameTimeMs`, status процесса, не только владельцев областей.
- **Нетерминизм:** запрет Date.now, Math.random, floating-point накопления денежных балансов; тест повторного воспроизведения.
- **Нагрузка:** не более 8–12 независимых отрядов на фракцию, фиксированная карта, расчёт pathfinding лишь при запросе/изменении графа, рендер интерполировать.
- **Пользовательское ожидание "реального времени":** gameplay и все игровые таймеры останавливаются при паузе; камера/UI продолжают работать — это обозначить в обучении.

## 8. План перехода после v0.1

**Шаг A — технический spike.** В отдельной ветке реализовать `SimulationClock`, pause/resume, x1/x2/x4 и несколько событий без интерфейсной экономики. Убедиться, что при одинаковых seed/очередях одинаковый итог независимо от 30/60/120 FPS.

**Шаг B — vertical slice.** Мини-карта из 4–6 областей; одна армия, одна шахта, одна стройка, одна вражеская армия. На паузе можно поставить 2–3 приказа, после возобновления они выполняются, можно снова поставить на паузу. Autosave mid-action.

**Шаг C — экономика и ИИ.** Перевести доход и upkeep в игровое время, ввести ограничение параллельных процессов; AI и игрок используют единый планировщик команд. Массовые seed-based симуляции на победы/длительность.

**Шаг D — полный режим.** Все 18 регионов и 3 эпохи; доступность портретного интерфейса, автопауза, инструменты обзора, возможность переключения между эпохами на паузе, ускорение.

**Шаг E — баланс.** Сравнить оба режима по длительности, завершению, winrate и частоте действий; принять решение, сохранять ли пошаговый режим как отдельный вариант.

Критерии spike: результат не зависит от FPS, отсутствие прогресса на паузе, корректное возвращение ресурсов при отмене, сохранение и загрузка mid-build/mid-march, пауза при background, latency UI не зависит от скорости. Нужны integration/e2e тесты на viewport 320×568, 390×844 и desktop.

## 9. Длительность одной партии — оценка, а не измерение

В `GAME_SPEC_V0.1.md` задано 20 раундов и максимум 3 AP на игрока за раунд. Максимум — **60 экономических решений за матч**, плюс выбор эпохи, осмотр карты и действия ИИ.

**Пошаговая v0.1 (проектные цели):**

| Сценарий | Оценка времени | Условия |
|---|---:|---|
| Опытный игрок, ПК | 15–25 мин | 20 ходов по ~45–75 сек, часть пропущена быстрым вводом |
| Новый игрок, ПК | 25–40 мин | чтение подсказок, сравнение построек, поиск карты |
| Опытный игрок, телефон | 20–35 мин | больше открытий карточек и камерных жестов |
| Новый игрок, телефон | 30–50 мин | малый экран и обучение |

Пример расчёта: 20 раундов × 60 секунд на планирование/три команды = 1200 секунд = **20 минут**; плюс 2–5 минут на обучение/финал. Автоматическое выполнение ИИ должно занимать секунды, а не минуты. Это **предположение**, а не статистика реальных игроков.

**Будущий RTwP:** выбрав, например, 12–18 игровых минут активного течения симуляции, получим реальное wall time от **15 до 35 минут**, так как на паузах игрок обдумывает стратегию; x2/x4 может уменьшить активное ожидание, но не обязательно общее время. Телефон потенциально дольше из-за чтения и очереди приказов. Точный прогноз невозможен без плейтестов: стратегия с автопаузой может занять дольше пошаговой из-за частого пересмотра приказов.

**После v0.1 измерять:** `matchStartedAt`, `matchFinishedAt`, `roundDecisionDuration`, `tutorialDuration`, `timePaused`, `timeSimRunning`, число открытых панелей, долю завершённых партий, причины досрочного выхода, медиану и p75 длительности. Для офлайн-версии собирать только локально с явным согласием на экспорт анонимной статистики; не отправлять данные в сеть без разрешения. Цели для итерации: медиана ПК ~20–25 мин, телефон ~25–35 мин; quick-mode ~10–15 мин и long-mode ~35–60 мин можно добавить позднее.

## 10. Оценка инженерной сложности

Поскольку исходная реализация отсутствует, оценки относятся к **дополнительной работе после качественной v0.1**. Для одного опытного разработчика с тестами: технический spike ~2–5 рабочих дней; vertical slice ~1–2 недели; полное покрытие экономики/AI/UI/balance ~3–8 недель; полировка/мобильный QA дополнительно ~1–3 недели. Это очень приблизительные диапазоны и не сроки выполнения Codex. Если domain engine переплетён с Phaser/DOM, трудоёмкость может существенно вырасти.

## 11. Финальное решение для Codex

**В релизе v0.1:** законченная пошаговая стратегия. Не заменять систему ходов на real-time по собственной инициативе, не включать кнопку паузы без полноценной семантики. **Архитектура:** pure domain engine, command validation, immutable/controlled state updates, seeded RNG, game events, тесты инвариантов. Полноценный RTwP — отдельный план работ после выхода и плейтестов v0.1.

### Технические первоисточники для дальнейшей проверки

- [MDN: requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame) — кадровая петля не эквивалентна игровому времени.
- [MDN: Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) — реакция на background.
- [Phaser documentation](https://docs.phaser.io/) — рендеринг, сцены и камеры.
- [Vite static deploy](https://vite.dev/guide/static-deploy) — возможность статического хостинга.

Этот документ — проектное исследование; расчёты длительности и сложности являются гипотезами для валидации, а не проверенными метриками.
